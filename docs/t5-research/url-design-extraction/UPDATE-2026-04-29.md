# Update — 2026-04-29

**Subject:** Pipeline hardening + dual-mode theming, driven by a real renderer (`apps/aiox-squad-design` DS Detail)
**Window:** 2026-04-28 → 2026-04-29
**Trigger:** Visual regression bugs surfaced when the React renderer started consuming `tokens-extended.json` verbatim.

The bench was originally written for a pipeline whose only consumer was the bundled `preview.html`. When the same artefacts were piped into a separate React app, dozens of fidelity bugs surfaced — outputs that looked fine in the preview but broke when re-rendered in a different shell. This update absorbs every fix needed to make the contract self-contained.

## New artefacts in `tokens-extended.json`

```json
{
  "schema_version": "1.1",
  "components": { … sanitised, with var() fallbacks injected … },
  "themed": {
    "defaultMode": "dark",
    "supportsDark": false,
    "light": { "--background": "#fff", "--text": "#111", … },
    "dark":  { "--background": "#000", "--text": "#fff", … },
    "preferred": { "--bb-canvas": "#0f0f11", … }
  },
  "coverage": {
    "detected": ["L1.colors_semantic", …],
    "missing":  [{ "category": "L3.backdrop_blur", "reason": "extractor_limitation" }],
    "reason_codes": { "extractor_limitation": "Signal exists in CSS but…", … }
  }
}
```

`themed` is the canonical theme block. `defaultMode` is what the live site renders by default; `supportsDark` is true only when the site is light-default but ships explicit dark vars (i.e. it has a togglable dark mode worth offering). Sites that are dark by composition (Linear, aioxsquad, Vercel, OpenAI, Anthropic when surface is dark) get `defaultMode: "dark"` and no toggle.

## New sibling artefact: `render-contract.json`

Higher-level contract emitted alongside `tokens-extended.json`. Aimed at downstream renderers that don't want to re-derive `theme.default_mode`, `surface`, `text`, etc:

```json
{
  "theme": {
    "default": "dark",
    "default_mode": "dark",
    "supports_dark": false,
    "supports_dark_reason": "dark-default surface; no toggle inferred from dark composition",
    "declared_default": "dark",
    "confidence": "high",
    "surface": "var(--background, #0f0f11)",
    "text": "var(--foreground, #f3f3f3)",
    "border": "var(--border, rgba(255,255,255,0.14))",
    "accent": "var(--primary, #d97757)"
  },
  "components": { "button": {…}, "card": {…}, "input": {…}, … },
  "native_vars": { "supports_dark", "preferred_selector", "preferred_count", "light", "dark", "preferred" },
  "warnings": [{ "code": "border_too_strong_for_dark_surface", "message": "…" }]
}
```

Renderers stop re-implementing the same fallback ladders (we had ~150 lines of `pickColorValue` / `pickOutlineValue` / `safeNumeric` / `normalizePadding` in the React app before this).

## `detectDefaultTheme` — signal hierarchy (final)

| Order | Signal | Confidence | Real example |
|---|---|---|---|
| 1 | `<meta name="color-scheme" content="dark light">` first token | high | Vercel → dark, GitHub → light |
| 2 | `<html data-theme="dark">` / `data-color-mode="dark"` | high | Linear, GitHub Primer |
| 3 | `<html class*="dark*">` / `<body class*="dark*">` | medium | aioxsquad |
| 4 | `<meta name="theme-color">` luminance | medium | Redpine (`#FFFFFF` → light) |
| 5 | **CSS background-var luminance** (NEW) | low | OpenAI (`:root:not(:where(.light)) { --color-background: #000 }` → dark) |
| – | Fallback | low | Apple, Anthropic, Shopify, Stripe, Nubank → light |

Signal #5 walks every block on `:root`, `:host`, `html`, `body`, classifies each by whether it applies as the **default** scope (rejects explicit `.light`/`.dark` selectors, but recognises `:not(:where(.light))` as default-applying), then averages the luminance of every `--background` / `--bg` / `--color-background` / `--surface` / `background-color` declaration found. Avg < 0.42 → dark, avg > 0.6 → light, otherwise inconclusive (defer to fallback).

## Theme classification rule (final)

Both `enrich.cjs` and `render-contract.cjs` now share the exact same rule:

```
1. theme-default.json has any non-fallback signal → trust verbatim
2. tokens.json surface luminance — direct signal of rendered surface
3. theme-default.json (any confidence) — last resort
4. light
```

Earlier iterations promoted "light + has dark vars" to dark globally — that broke Redpine (light surface, dark modal vars). Earlier iterations also gated on `confidence === "high"` only — that left OpenAI at light because its CSS-bg signal is "low" by definition (statistical heuristic). The current rule trusts any pick from a detector that found *something*, falling back to surface luminance when the detector returns `no-signal-fallback`.

## Renderer simplifications enabled by these changes

The React DS Detail app currently still ships its own defensive layer:

Every one of these duplicates work the pipeline now does. They become legacy paths once we've validated 30 days without regressions on extracts emitted by the new pipeline. Estimated ~150 lines of UI removable.

## What I would still ask of the pipeline

1. **Component disambiguation by DOM proximity** — the Nubank button bug came from Swiper arrow rules merging into `components.button`. A future detector pass keyed on snapshot DOM tree would emit `nav-button`, `cta-primary`, `carousel-arrow` separately rather than agglomerating.
2. **Selector provenance per token** — for each emitted property, persist the source selector + occurrences. Renderers could downgrade confidence on rules that came from a single match in `.shake-error`.
3. **Strict schema versioning** — `schema_version: "1.1"` is set but not enforced. Renderers should reject incompatible majors.
4. **Preview URL validation** — `https://example` placeholders still leak into `preview.html`. Pre-write hook with `URL.hostname` + TLD shape check would close it at source.

These are tracked in the existing `gap-absorption-roadmap.md`; this update bumps their priority based on real visual regressions.
